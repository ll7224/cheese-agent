# Cheese Agent 求职作品推进方案

日期：2026-10-16；2026-10-17 更新。**当前主线已调整：** 用户希望Cheese承担真实App开发，而不只是求职展示。现阶段进入[数字小猫App产品设计](../specs/2026-10-17-digital-cat-product-brief.md)，已确认原生iPhone App及异步离线生活方向，不采用Web/PWA首版；本方案的求职包装与批量评估暂缓，保留为历史规划。

已完成的工程基线：M0完成，M1维护/交付出口达到。同名分组后续修正由Cheese在新会话完成，23步、约4分19秒、498,933 Token，干净副本构建及外置16项通过；案例冻结。M2尚未开始。见[案例记录](../../showcase/CASE_STUDY.md)。

> 后续获得实施授权后，主代理按里程碑执行并负责修改、取舍和最终验证；子代理只做一次性只读探索。执行可使用 `superpowers:executing-plans`，本方案不授权提交 Git、发布代码、部署公网服务或使用付费模型。

**Goal：** 为有前端经验、面向杭州 AI 应用 / Agent 开发岗位的求职者，交付一个可演示、可复现、能深入解释的工程维护 Agent 作品。

**Architecture：** 保留 TypeScript、Hono、原生 Web、Runtime/worker 和现有知识服务。围绕一个外部前端项目的维护任务贯通执行与交付；评估复用真实 Runtime/worker，不另外搭建 Agent 引擎或评测平台。

**Tech Stack：** 现有 TypeScript、Vercel AI SDK、Hono/SSE、SQLite、node:test；不为求职包装迁移 Python、React 工作台或其他 Agent 框架。

**Spec：** 本次对话确定的方向及本文第 1–3 节；原有能力与限制参考[本机工作台](../../local-web-workbench.md)、[工程知识设计](../specs/2026-10-13-engineering-knowledge-design.md)和[历史验收](../../verification/local-agent-ui.md)。历史计划中未落地的能力不视为本轮已有能力。

## 1. 对外定位与完成标准

定位：**面向 TypeScript/前端项目的小范围工程维护 Agent，结合源码与项目约定交付可审查补丁、验证结果和依据。**

它是个人工程作品，不以替代成熟通用编码工具为目标。招聘展示只讲三件事：

1. 能把一个真实问题从输入推进到经过验证的代码修改。
2. 能管理执行过程，包括停止、失败和恢复，区分运行结束与任务成功。
3. 能用公平对照判断知识增强的收益与成本，而不是把接通 API 当效果证明。

本轮完成需要以下五项：

- 一个可在本机从干净起点重现的维护案例，以及一段约 3 分钟录屏。
- 一组基础配置/知识增强对照：先冻结6题初批（2个开发样例、4个保留任务），根据费用与诊断价值决定是否扩至原目标10题；开发与保留结果分开报告，保留失败原因。
- 两个讲得透的技术主题：可控执行、知识如何影响执行。
- 可运行的 README、示例配置、基础 CI 和明确的能力边界。
- 一页项目介绍、两条有事实支撑的简历项目要点及一次面试讲解练习。

完成这些即可用于投递，不以知识增强胜出、所有任务通过或获得真实商业用户为前提。

## 2. 全局约束与暂不投入项

- 保留既有 CLI/Web/Channel 使用方式。评估开关只作用于显式选择的评估运行；未传新选项时保持原行为，不给旧调用增加前置条件。
- 不重写整个运行时，不迁移工作台框架，不把既有大文件作为新增逻辑容器。新增逻辑独立模块，既有入口做必要接线。
- 暂停新增渠道、更多领域角色、图谱扩展、插件市场、多用户、云部署和视觉主题重做；保留已有功能，不为“收缩”做删除清理。
- 不使用雇主私有代码、真实客户资料、凭据或未经授权的历史会话作为展示材料。
- 真实执行仅限本机、可信仓库的独立副本。工作目录隔离不宣称为 OS 沙箱；不给陌生人开放远程 shell。
- 每阶段集中做一次相关检查和必要构建，失败只重跑受影响部分；不默认全量测试、双重审查或浏览器矩阵。
- 真实模型评估是本轮求职证据，不是新增日常回归门槛。批量调用前由用户选择模型和费用上限；超过上限停止，不自动换模型。
- 不预设“提升百分比”，不隐藏失败；没有计量数据时记为缺失，不填零或猜成本。

## 3. 当前基线与必须补齐的缺口

本节依据 2026-10-16 的只读检查；本轮没有运行应用或重跑历史测试。

| 当前情况 | 本轮处理 |
| --- | --- |
| Runtime 已有任务提交、幂等、worker、取消、事件持久化及订阅 | 直接复用，不重造编排框架 |
| 知识服务已有检索、引用、版本、候选/生效与纠错 | 选一个明确机制做对照，不把全部知识能力都塞入展示 |
| `sample-project/` 只有三个带演示注释的源码文件 | 保留原样；不把它包装成真实 React 维护案例 |
| Web 可以展开工具事件，但没有专门 diff 或执行报告导出 | 首案例先用工具输出与独立 diff 文件；最后只补轻量结果摘要 |
| Web 的 `runTask` 未传 UsageTracker，API 没有逐运行 usage | 增补结构化计量事件，供评估和结果摘要共同消费 |
| `rag.enabled=false` 不是 Web 的完整无知识开关；JIT 与自动沉淀另有入口 | 增加显式评估策略，覆盖注入、检索和沉淀，不靠一个配置字段假装完成对照 |
| JIT 当前使用 `getCliKnowledgeService()`，Web 检索通过 Runtime RPC | 检查演示路径是否用同一库、作用域和运行上下文；未接通时先修连接，不把“命中空库”算增强实验 |
| 有历史真实模型工具调用烟测，没有查到维护任务效果对照或 CI 工作流 | 补任务级证据和最小 CI；不照搬历史测试数量当当前结果 |
| README 有“生产级”“沙箱”等宽泛宣传，MIT 链接没有对应许可证文件 | 按实际边界重写；公开前由用户确定许可证，不代选或虚构授权 |

关键接入位置：`src/runtime/service.ts` 的 `submit/execute/events/idle`，`src/runtime/worker-client.ts`，`src/runtime/worker.ts`，`src/main.ts` 的 `runTask`，`src/agent/loop.ts`，`src/runtime/events.ts`。实施前完整读取实际要修改的函数及相关调用。

## 4. 推进节奏

建议以 **2–3 周、每周约 10–15 小时**作为首轮时间盒，不作为固定交付承诺。首案例完成后校正剩余工作量；时间不足先减任务集规模或界面范围，不继续扩平台。

| 里程碑 | 建议投入 | 交付与出口 |
| --- | --- | --- |
| M0：锁定样本和任务 | 2–3 小时 | 可用项目、一个缺陷、固定起点、验收标准 |
| M1：打通真实维护闭环 | 6–10 小时 | 实际运行、补丁、独立验收和失败记录 |
| M2：形成效果证据 | 8–14 小时，另计模型等待 | 小型对照、结果表、一次针对性改进 |
| M3：整理展示并开始投递 | 5–8 小时 | 录屏、README、技术复盘、CI、简历要点 |

M1 结束即可把项目加入简历初稿并筛岗位；M2 的数据补齐后开始定向投递，不等待额外功能。

### 4.1 案例通过后的实际顺序

下面是当前优先级，替代继续扩展cmdk边界或直接批量调用模型。投入为工作量估计，不是固定完成日期。

| 顺序 | 投入 | 负责与交付 | 完成标准 |
| --- | --- | --- | --- |
| 0. 处理凭据暴露 | 先处理 | 用户轮换本次检查中进入未筛选工具输出的模型API密钥；主代理在下一轮实施中收窄session查询响应，补凭据不外泄的接口回归 | 旧密钥失效；查询不返回密钥值。轮换前不发起真实模型调用，文档和本地工作继续 |
| 1. 整理展示初版 | 约3–4小时 | 主代理重写README首页，写`docs/showcase/INTERVIEW.md`及3分钟演示脚本，整理两条有证据的简历要点；用户确认本人负责内容并录屏 | 陌生读者1分钟内看懂定位，用户能讲清问题、执行、验证及失败改进。无证据的生产级/沙箱/性能宣传删除，中英文一致 |
| 2. 补可复现交付 | 约3–5小时 | 主代理提供干净起点的准备/外置验收命令、脱敏示例配置、最小CI；做一次干净安装检查 | 非本机硬编码入口可复现；无需付费API的关键检查能在CI执行。真实模型与历史回放明确区分；用户确定许可证后才公开 |
| 3. 做第一批效果对照 | 约6–10小时，另计模型等待 | 主代理先准备6题（现有2题开发样例＋4题未用于调优的保留题），跨两个项目，完成知识off/read-only策略、轻量runner和逐任务报告；用户确认模型及费用上限再执行 | 同任务同输入成对比较通过、耗时、已观测Token、介入和失败原因。先报6题初批，再根据费用与问题价值决定是否扩到原目标10题；知识没有提升也保留结果 |
| 4. 形成投递反馈 | 首包就绪后并行 | 主代理筛5–8个杭州AI应用/Agent/AI全栈岗位并对齐材料；用户做一次10分钟讲解、投递 | 不把两次开发样例当通用成功率；缺少知识对照时只写已验证的执行可靠性，数据补齐后再更新 |

首个展示版本复用现有会话和补丁，不为录屏反复请求模型；可展示历史执行并明确标注，等待过程允许加速。现有结果摘要或独立证据文件已足以讲解时，不把新UI组件作为先决条件。暂不新增角色、渠道、图谱、插件、云部署或框架迁移。

## 7. M2：做小型对照，确认知识增强是否值得

### 7.1 先补正确的运行策略和计量

**新增职责边界：**

- `src/runtime/execution-policy.ts`：显式评估策略及默认值，独立于普通用户配置。
- `scripts/eval/run.ts`：准备独立副本、调用真实 Runtime、等终态、运行裁判、保存结果。
- `scripts/eval/report.ts`：将结果归并为逐任务对照和简短汇总。
- `scripts/eval/types.ts`：任务和结果数据契约；不建设数据库、服务或评测管理 UI。

**接线：** `src/runtime/service.ts`、`worker-client.ts`、`worker.ts`、`src/main.ts`、`src/agent/loop.ts` 和 `src/runtime/events.ts`。模块新增逻辑不集中塞进 service/main。

建议的策略接口：

```ts
export interface ExecutionPolicy {
  knowledge?: 'off' | 'read-only' | 'read-write';
}
```

缺省保持现有行为。`off` 禁止知识工具、知识专用提示、JIT 和自动沉淀；`read-only` 使用固定知识内容，但禁止导入、记录守则、纠错和结束后沉淀；`read-write` 沿用正常路径的既有配置。策略由 Runtime 编程入口显式传入并传递给 worker，不开放一个默认关闭安全控制的公网参数。

- [ ] 确保主任务和派生任务不绕过显式策略。首轮配对评估固定关闭子代理，避免把并行策略变化误算为知识收益；日常功能保留。
- [ ] 两组使用全新会话、记忆目录、知识目录和工作副本；相同模型、版本、生成参数、根提示词、技能、基础文件/shell工具、步数及超时预算。唯一处理差异是知识服务及其必要提示。
- [ ] 基线仍可读取同一批项目文档和约定、搜索同一份源码；增强组只是获得这些材料的索引与有出处的知识，不能额外获得任务答案。
- [ ] 在模型调用结束处发送可持久化的 usage 事件，关联 run、step、attempt 和适用的 childRunId。累计供应商确实返回的输入/输出数据；缓存字段按供应商口径处理，不重复叠加。
- [ ] 重试和异常结束也保留已返回的 usage；缺失部分标为未知，报告“已观测用量”，不伪装完整费用。没有当前价格依据时只报告 token，不估美元/人民币。
- [ ] runner 保存请求到终态耗时、工具调用数、人工介入、补丁、裁判结果和失败分类。事件与材料脱敏，不发布凭据、绝对私有路径或完整内部推理内容。

**最小检查：** 用可控模型覆盖默认策略兼容、知识关闭、只读禁止写入、计量缺失与累计；复用现有 `tests/knowledge-core.test.ts`、`tests/worker.test.ts` 和 runtime 夹具，新增测试仅覆盖新契约。

### 7.2 冻结任务集，再调用真实模型

- [ ] 先在两个项目冻结6题初批：现有2个开发样例、4个未用于调优的保留任务；必要时扩至原目标10题（2开发、8保留）。覆盖请求/状态、接口类型、边界行为；每题都有固定起点和裁判，开发与保留结果分开统计。
- [ ] 任务来源与构造方式逐项标注。知识快照只包含任务开始时可获得的内容，排除参考答案、修复提交、评估报告和另一组的运行产物。
- [ ] 使用开发样例跑通 runner，预估调用量，由用户确定模型与费用上限后再开始批量评估。不开自动重试付费批次，不为追求好看的结果无限重复。
- [ ] 每个保留任务每组先运行一次，交错两组执行顺序，固定相同并发条件。不宣称小样本具有统计显著性；结果有分歧时按事先说明的规则对该任务成对补跑，并保留全部结果。
- [ ] 展示逐任务是否通过、人工介入、耗时和已观测 token。辅助完成不能混入自主完成率；失败运行不能从分母或成本表中删除。
- [ ] 只针对最大失败类别做一轮改进，在开发样例验证。若改进参考了保留任务，则把这些任务标为诊断集，不能继续称为未见评估；新增少量未见任务复核时单独列结果和费用。

## 9. 决策与责任

| 情况 | 处理 |
| --- | --- |
| 没有合适的私有项目授权 | 主代理选择允许使用的公开小项目，不读取雇主源码 |
| 模型或调用费用未确定 | 先完成 fixture 与 runner，真实批次等待用户选择模型和费用上限 |

| 没有可公开录屏的真实模型运行 | 先交付标注清楚的回放；真实演示证据仍未完成，不声称已交付 |
| 遇到许可证或发布权限问题 | 本机工作继续，公开发布由用户确认后进行 |

用户负责真实场景判断、隐私/发布授权、模型费用和面试表达；主代理负责样本筛选、实施、证据整理与最小验证。子代理只用于独立只读定位，不承担代码修改和最终验收。
